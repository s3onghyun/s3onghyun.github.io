nvim-edu를 만들며: 브라우저 Vim 연습장을 진짜 Neovim에 맞추기

이 글은 같은 프로젝트를 다룬 글을 블로그용으로 다시 쓴 제작 기록이다. 만든 사람이 자기 레벨을 못 푼 이야기 위주의 짧은 버전은 velog, dev.to, Zenn, Qiita에도 올렸다.

요즘은 IDE보다 터미널을 여는 날이 많다. Claude Code나 Codex 같은 에이전트를 tmux 창에 띄워 놓고 결과를 본다. 그래도 에이전트가 고친 코드를 사람이 마지막에 손보는 순간은 남아 있고, 그때 손이 가는 건 터미널 안의 Neovim이다. 문제는 내가 Vim을 잘 못 쓴다는 점이었다. :wq에서 거의 멈춰 있었다.

그래서 연습장을 만들었다. nvim-edu는 설치 없이 브라우저에서 Vim·Neovim·tmux 키를 연습하는 사이트다. LearnGitBranching처럼 목표 상태를 보여 주고, 그 차이를 키보드로 메우게 한다. 2026년 10월 13일에 첫 커밋을 했고, 처음부터 Claude Code와 같이 만들었다. 커밋 메시지에 Claude 공동 작성자 표기와 세션 링크가 남아 있다.

만들고 싶었던 것

요구지금 모습
목표를 보고 차이를 메우는 방식왼쪽은 내 버퍼, 오른쪽은 목표. 아직 다른 줄은 빨갛게 표시
잘 푼 정도를 숫자로레벨마다 모범 답안의 키 수(par)를 두고 ★1~3
에이전트 옆에서 실제로 쓰는 상황실전 챕터의 보스가 “리뷰 코멘트 반영”이고, tmux 챕터가 따로 있음
손버릇을 바로잡기1장(이동)에서는 방향키와 마우스를 막고, NORMAL 모드에서 한글 IME로 치면 한/영 전환 안내
Neovim처럼 보일 것neo-tree 사이드바, bufferline, lualine, 상대 줄 번호, :colorscheme tokyonight 같은 테마 전환

지금은 레벨 41개가 있다. 이동, 편집, 텍스트 오브젝트, 비주얼·매크로, 실전(:%s, :g), tmux, 구루 콤보 순서이고 챕터마다 초보부터 구루까지 난이도 배지를 붙였다. 레벨 사이에는 랜덤 10라운드 미션과 날짜를 시드로 쓰는 오늘의 미션이 있다.

가장 큰 선택: 에뮬레이터냐 진짜 Neovim이냐

브라우저에서 Vim을 돌리는 방법은 크게 두 가지다.

방식장점단점
@replit/codemirror-vim 같은 에뮬레이터바로 뜨고 가볍다. 화면과 채점을 JS에서 마음대로 다룰 수 있다진짜 Vim과 동작이 조금씩 다르다
vim.wasm으로 실제 Vim 실행동작이 진짜다첫 로딩이 무겁고, 상태를 JS로 꺼내기 까다롭다. SharedArrayBuffer가 필요하다

연습장은 키 한 번에 바로 반응해야 해서 기본은 에뮬레이터로 갔다. CodeMirror 6에 codemirror-vim을 얹었다. 걸리는 건 “에뮬레이터가 틀리면 틀린 습관을 가르치게 된다”는 점이었다. 그래서 실제 Neovim을 정답지로 두고 차이를 계속 재기로 했다.

깊이 보기 1: 같은 키를 nvim --headless에 넣어 비교하기

tests/nvim-diff.mjs는 같은 키 입력을 실제 Neovim과 사이트 에디터에 넣고 텍스트, 커서, 모드를 비교한다. 케이스는 :help의 motion.txt, change.txt 등에서 자주 쓰는 명령과 모든 레벨의 모범 답안이다.

Neovim 쪽은 Lua 스크립트 하나로 돈다. 케이스마다 새 버퍼를 열고, 키를 넣고, 결과를 JSON으로 적는다.

-- nvim --clean --headless -l runner.lua in.json out.json
for _, c in ipairs(cases) do
  vim.cmd('enew!')
  vim.bo.undolevels = -1 -- 초기 텍스트는 undo 대상이 아니게
  vim.api.nvim_buf_set_lines(0, 0, -1, false, vim.split(c.text, '\n', { plain = true }))
  vim.bo.undolevels = 1000
  vim.api.nvim_win_set_cursor(0, { c.cursor[1] + 1, c.cursor[2] })
  local ok, err = pcall(vim.api.nvim_feedkeys, vim.api.nvim_replace_termcodes(c.keys, true, false, true), 'xtn', false)
  -- 텍스트, 커서(바이트가 아니라 글자 단위 열), 모드를 기록
end

사이트 쪽은 빌드한 결과를 vite preview로 띄우고 Playwright로 같은 키를 실제로 누른다. 레지스터나 매크로가 섞이지 않게 케이스마다 페이지를 새로 연다. CI에는 이 비교만 하는 잡이 따로 있고, 로컬에서 쓰는 것과 같은 Neovim 0.11.0을 받아서 돌린다. 이 잡이 깨지면 배포가 되지 않는다.

- name: Neovim 0.11.0 설치 (로컬 비교 기준과 같은 버전)
  run: |
    curl -fsSL https://github.com/neovim/neovim/releases/download/v0.11.0/nvim-linux-x86_64.tar.gz | tar xz -C "$RUNNER_TEMP"
    echo "$RUNNER_TEMP/nvim-linux-x86_64/bin" >> "$GITHUB_PATH"
- run: npm run test:nvim

처음 돌렸을 때는 169개 중 130개만 일치했다. 39개가 달랐다.

깊이 보기 2: 에뮬레이터를 Neovim 쪽으로 고치기

차이는 대부분 Neovim 기본값이나 경계 조건에서 나왔다. 몇 가지를 꼽으면 이렇다.

  • 검색과 :s가 대소문자를 항상 무시했다. ignorecase·smartcase(기본 꺼짐)와 \c \C를 따르게 고쳤다.
  • dG가 빈 줄을 남겼고, v$d는 줄바꿈을 지우지 않았다.
  • Ctrl-a가 007을 8진수로 봤다. Neovim 기본값은 nrformats=bin,hex라서 8진수로 보지 않는다.
  • Neovim 기본값인 nostartofline을 따르지 않아 G, gg, >> 뒤에 커서 열이 달라졌다.
  • 첫 줄에서 k, 마지막 줄에서 j는 실패해야 하고, 매크로는 이동이 실패하면 멈춰야 한다.
  • df에 없는 글자를 주면 실제 Vim은 아무것도 안 하는데, 에뮬레이터는 제자리를 돌려줘서 한 글자를 지웠다.

수정은 포크하지 않고 patch-package로 patches/에 두었다. npm install의 postinstall에서 자동으로 적용된다. 업스트림 버전이 오르면 패치가 깨질 수 있지만, 그때는 nvim-diff가 바로 알려 준다. 나중에 구루 챕터를 만들면서 정규식 그룹(\( \), \1)이 매치되지 않는 것도 찾았다. 에뮬레이터가 JS 정규식 문법을 쓰고 있어서 실제 Vim 문법을 따르도록 바꿨다. 케이스가 늘어 지금은 180개 모두 일치한다.

깊이 보기 3: 진짜 Vim 모드와 titlestring

그래도 “진짜로 해 보고 싶다”는 사람을 위해 vim.wasm으로 실제 Vim 8.2를 띄우는 진짜 Vim 모드(beta)를 붙였다. Neovim 기본값에 맞추려고 vimrc에 nostartofline, nrformats=bin,hex, nnoremap Y y$ 같은 설정을 넣는다.

어려웠던 건 채점이었다. 버퍼 상태를 JS에서 꺼내야 하는데, 명령 도중에 JS가 cmdline을 넣으면 Vim이 멈췄고, autocmd 안에서 내보내면 교착 상태가 됐다. 둘 다 실제로 돌려 보고 알았다. 결국 Vim이 화면을 다시 그릴 때 스스로 보고하게 했다. 창 제목을 상태 JSON으로 만드는 방법이다.

function! EduState()
  return json_encode({'lines': getline(1, '$'), 'line': line('.') - 1,
        \ 'col': strchars(strpart(getline('.'), 0, col('.') - 1)), 'mode': mode(1)})
endfunction
set title titlelen=0 titlestring=%{EduState()}

SharedArrayBuffer를 쓰려면 COOP/COEP 헤더가 필요한데 GitHub Pages는 이 헤더를 붙일 수 없다. 그래서 /real/ 페이지에만 coi-serviceworker를 적용해 우회했다. Safari에서는 이 우회가 첫 방문에만 동작해서, 오류 대신 안내 문구를 띄운다. 첫 로딩은 처음에 약 2.1MB였는데, 빌드할 때 Vim 런타임에서 레벨에 필요한 파일(js, py, yaml, txt용)만 남겨 0.8MB로 줄였다.

깊이 보기 4: tmux는 시뮬레이터로

tmux는 브라우저에서 돌 수 없다. 키 바인딩은 수백 개지만, 에이전트를 돌리면서 사람이 실제로 누르는 키는 몇 개 안 된다. 세션 만들기와 떼고 붙기, 화면 나누기와 이동, C-b z 확대, 그리고 copy mode로 긴 에이전트 로그를 스크롤해서 에러를 복사하는 것 정도다.

그래서 이것만 흉내 내는 시뮬레이터를 따로 만들었다. src/tmux.js는 DOM이 없는 순수 상태 머신이고, 세션·윈도우·pane 트리와 prefix C-b, vi copy mode, 붙여넣기, 작은 셸을 갖고 있다. 화면 그리기는 src/tmux-view.js가 맡는다. 상태 머신이 DOM과 떨어져 있어서 node --test로 바로 테스트하고, 모든 tmux 레벨 답안을 브라우저 없이 검증한다. 명령 프롬프트(C-b :), 마우스, pane 크기 조절은 일부러 넣지 않았다.

무엇이 잘못됐나

  • 레벨을 다 만들고 직접 눌러 보라는 확인 요청을 받았는데, 모범 답안 3lxfmx를 못 읽었다. Claude가 키 → 뜻 → 결과 단계표로 풀어 주고 나서야 이해했다. 지금 사이트의 풀이 해설도 같은 형식으로, 클리어한 뒤 내 키와 모범 답안을 Vim 명령 단위로 끊어 다시 실행해 보여 준다.
  • 한글 입력 상태로 NORMAL 모드에서 jjl을 치면 커서는 그대로고 ㅓㅓㅣ가 찍혔다. 처음엔 트랜잭션을 거부했는데, 커서가 줄 끝으로 튀고 이후 영문 키가 글자로 들어갔다. 지금은 inputHandler로 받아서 조합을 강제로 끝낸다. 이런 버그는 tests/regress.e2e.mjs에 재현 테스트로 남겼고, 고치기 전 버전에서 14개 중 9개가 실패하는 걸 확인했다.
  • u가 동작하지 않았다. CodeMirror의 history 확장을 빠뜨렸던 것이다.
  • 진짜 Vim 모드에 키를 0ms 간격으로 넣으면 vim.wasm이 순서를 섞었다. 사람 속도인 40ms 간격에서는 문제가 없어서 테스트도 그 속도로 입력한다.

테스트로 지키는 것

CI는 chromium, firefox, webkit 세 브라우저에서 모든 레벨 답안과 미션 150라운드를 실제 키 입력으로 풀어 보고, 영어 화면에 한글이 남지 않았는지도 본다. 레벨을 추가하려면 src/levels.js에 객체 하나를 넣으면 되고, solution이 곧 par가 된다. npm test가 그 답안으로 실제로 클리어되는지 확인한다.

다음 할 일

  • 물리 키보드가 있어야 한다. 모바일 터치 입력은 아직 안 된다.
  • 진행 상황은 브라우저 localStorage에만 저장된다.
  • Safari의 진짜 Vim 모드는 헤더를 붙일 수 있는 호스팅으로 옮기면 풀린다.
  • “이런 상황이 레벨로 있었으면 좋겠다”는 제안은 이슈나 PR로 받는다.
